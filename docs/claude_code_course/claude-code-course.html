Claude Code CLI is not a smarter autocomplete. It is an autonomous agent that reads, writes, builds, and reasons about your codebase. Most users only ever see the surface — the chat loop. Module 01 — Orientation

Lesson goal

By the end of this lesson you have Claude Code installed, running against pacman-cpp20, and a clear mental model of what it is — not what the marketing says, what it actually does. You should be able to explain the REPL loop, the difference from Claude Desktop, and name all three architecture layers without looking.

1.1 — What Claude Code is not

Claude Code is not an IDE plugin. It is not a chat interface with file access bolted on. It is a shell-resident autonomous agent. It runs in your terminal. It reads your filesystem. It executes commands. It writes files. It builds your project. The REPL is just how you give it the initial directive — after that, it acts.

The key difference from Claude Desktop or claude.ai: those are conversation tools. Claude Code is an execution agent. The gap is not cosmetic.

1.2 — Installation

# Requires Node.js 18+
npm install -g @anthropic-ai/claude-code

# Authenticate (opens browser)
claude

# Confirm version
claude --version
Subscription vs API key
A Pro or Max subscription gives you a fixed monthly allowance — preferable if you use it consistently. API key access charges per token — preferable if usage is irregular or you want to avoid rate limit windows. For this course, either works; the features are identical.

1.3 — Three modes of operation

claude

Interactive REPL. Maintains full conversation context across turns. Compacts automatically when the context window fills. This is your primary mode.

claude -p "your task here"

Print mode — single query, exits. No persistent context. Useful for scripting, one-shot analysis, piped input.

claude --resume

Resume the most recent session. Context from the last run is reloaded. Critical for multi-day work on a single task.

1.5 — The delegation tiers (from your project)

Your pacman-cpp20 project already defines a four-tier human-AI delegation model. This maps cleanly to how you should think about Claude Code tasks:

T1
Author drives, agent is silent. C++20 feature implementations, architectural decisions, ghost AI logic. You write it. Claude does not touch it until you request a review.

Module 02 — Configuration hierarchy & CLAUDE.md drift audit

Lesson goal

By the end of this lesson you have a clear mental model of the configuration hierarchy, you understand why CLAUDE.md is a test against the codebase rather than static documentation, and you have hands-on experience with the three-step audit pattern. You will have applied it to the real pacman-cpp20 CLAUDE.md, which has drifted from the actual codebase state.

2.1 — The configuration hierarchy

Claude Code assembles its behaviour from four overlapping layers, applied in this order (later layers override earlier ones):

1
Global
~/.claude/CLAUDE.md · ~/.claude/settings.json
Your identity as an engineer. Applies to every project on this machine. Good place for personal code style preferences, communication style, and universal rules ("always explain what you changed and why").
2
Project
CLAUDE.md · .claude/settings.json · .claude/rules/*.md
Git-committed. The shared contract for the project. Build commands, architecture, conventions, delegation tiers. Every team member (and every session) starts from the same baseline.
3
Local
CLAUDE.local.md · .claude/settings.local.json
Not committed. Personal overrides for this machine. Current WIP state, session notes, things you want Claude to remember that are not for the team.
4
Env
ANTHROPIC_MODEL, MAX_MCP_OUTPUT_TOKENS, etc.
Runtime overrides. Useful in CI/CD pipelines, container environments, or when switching model tiers mid-project without editing files.
The practical implication
When Claude Code behaves unexpectedly, the first question is: which layer is controlling this? A global CLAUDE.md instruction can silently override a project convention. Knowing the hierarchy tells you where to look.

2.2 — CLAUDE.md as a falsifiable test

The common failure mode: developers write CLAUDE.md once, commit it, and never touch it again. Three months later the build commands changed, two new modules were added, and Phase 2 closed — but the file still describes the project as it was.

This matters more than it would for ordinary documentation, because Claude Code acts on the file. Stale build commands mean it runs the wrong command and gets confused by the failure. A stale module graph means it makes incorrect assumptions about dependencies. A stale phase status means it may attempt things that are already done.

The mental model shift
Stop treating CLAUDE.md as documentation — documentation describes intent. Start treating it as a test suite — every claim is falsifiable. "The module graph looks like X" is a claim the source tree can confirm or contradict. "Phase 2 is near-complete" is a claim the code can confirm or contradict. When the codebase contradicts a claim, that is a failing test. The audit is the test run.

2.3 — The three-step audit pattern

This pattern applies any time you suspect drift — after a sprint, after a refactor, when resuming a project after a break. It is also the general pattern for any Claude Code task that touches living documentation.

Step 1
Read-only
Audit — find the contradictions. Ask Claude Code to cross-reference CLAUDE.md against the source tree and list every claim that is stale, missing, or contradicted. No writes. No suggestions about what to add. Just a report: here is what the file says, here is what the code says, here is the delta.
Step 2
Human
Review — own the decision. Read the audit report. For each finding: accept it, override it, or flag it as something Claude Code missed. This is the T2 moment — you are driving. The agent surfaced the information; you decide what to do with it. Some "stale" items may be intentional. Some things Claude Code did not flag may be more important than what it did.
Step 3
Targeted
Edit — apply only what you approved. Ask Claude Code to apply the specific changes from your reviewed list. Not "rewrite CLAUDE.md" — that loses intentional content and produces a file that belongs to the agent, not to you. Targeted edits to specific sections. You read every changed line before committing.
The trap to avoid
The tempting shortcut: "Rewrite CLAUDE.md to match the current codebase." Do not do this. A free-form rewrite will silently discard intentional decisions — the delegation tier model, the coding conventions, the design principles — because they are not directly reflected in source files. The three-step pattern exists specifically to protect the parts of CLAUDE.md that express intent, not just state.

2.4 — Modular rules

For larger projects, a monolithic CLAUDE.md becomes unwieldy. Claude Code supports splitting rules into separate files under .claude/rules/. Each file is a focused contract for a specific concern.

.claude/rules/
├── code-style.md      # naming, formatting, what to never do
├── build.md           # build commands, presets, output paths
├── architecture.md    # module graph, layer boundaries, invariants
└── delegation.md      # T1–T4 tiers, commit tag conventions

The top-level CLAUDE.md can then be a short index — what each rules file covers and when it applies. For pacman-cpp20 the monolithic file is fine at current scale, but knowing this exists prevents the "one giant file" trap as the project grows.

After Module 2, your CLAUDE.md should satisfy this checklist. Run it mentally before every commit of the file:

  • Build commands use preset syntax, not the legacy -B/-G form.
  • Output paths match the preset config (out/build/<preset>, not build/).

Module 03 — Permission model & gating tool execution

Lesson goal

By the end of this lesson you have a precise mental model of how Claude Code asks for — and acquires — permission to act. You understand every permission mode, know when each is appropriate, and can configure --allowedTools / --disallowedTools to gate execution to exactly the surface you want to expose. You will have practised running Claude Code in read-only mode, in auto mode, and in plan mode against pacman-cpp20.

3.1 — Why permissions matter here

Claude Code is an execution agent. The same property that makes it powerful — it acts — is what makes the permission model important. A misconfigured session can write files you did not intend, run build commands at the wrong time, or — in a worst case — touch things outside the project root.

This is not a theoretical risk. It surfaces in practice when you run Claude Code in a shared codebase, in CI, or when you hand it a broad task without constraining its tool surface. The permission model is the mechanism that lets you match the agent's action radius to the trust you are actually willing to extend.

The right mental model
Think of permissions like function signatures. A function that takes no parameters and returns a value is safe to call without side effects — it is read-only. A function that takes a mutable reference to your filesystem and has no return type deserves more scrutiny. The permission system is how you control which signature Claude Code is allowed to call.

3.2 — The five permission modes

Claude Code ships with five permission modes. They are set via --permission-mode on the CLI, or via permissionMode in .claude/settings.json. Later layers override earlier ones — a project setting overrides global, a CLI flag overrides a project setting.

default
Ask before every action. Claude Code prompts before each tool call that has side effects — file writes, shell commands, web requests. The safest mode. Use it when you are still learning what a session will do, or on an unfamiliar codebase. The cost is interruption: every non-trivial task becomes a series of approval dialogs.
acceptEdits
Auto-approve file writes, ask for shell commands. File edits are approved silently; shell execution still prompts. The most common daily-driver mode for active coding sessions. You trust the agent to write files — you still want to see before it runs a build or a script.
auto
Approve everything except explicitly disallowed tools. No prompts. The agent works at full speed. Appropriate when you have a well-defined task, a clean worktree, and you understand the tool surface. In practice: use this with --disallowedTools to remove anything destructive, and you get speed without loss of safety.
dontAsk
Never prompt, never block. Maximum autonomy. Use in headless CI/CD pipelines where there is no human in the loop. Dangerous in interactive use — the agent will execute anything, including commands you did not expect. Pair it with tight --allowedTools constraints if you use it outside of CI.
plan
Read-only reasoning — no execution. Claude Code reads files, reasons, and produces a plan. It cannot write or execute. This is the mode for exploration, review, and architectural reasoning where you want the agent's analysis but not its hands on the codebase. Also useful as a dry-run before switching to auto.

3.3 — Tool gating with --allowedTools and --disallowedTools

Permission modes set the general policy. Tool gating lets you override that policy at the level of individual tools. The two flags are composable and apply at the CLI or in .claude/settings.json.

# Read-only session: allow only file reads, block everything else
claude --allowedTools Read,LS,Glob,Grep

# Auto mode, but never touch git or run scripts
claude --permission-mode auto --disallowedTools Bash,GitCommit,GitPush

# CI pipeline: headless, only build and test commands permitted
claude --permission-mode dontAsk --allowedTools Bash,Read
The tool surface for pacman-cpp20
The tools Claude Code has available fall into four categories: Read (Read, LS, Glob, Grep — no side effects), Write (Write, Edit, MultiEdit — modify files), Execute (Bash — run shell commands), and Agent (Task — spawn subagents, covered in M7). For a typical pacman-cpp20 coding session, acceptEdits mode covers Read + Write silently, and still asks before Bash. That is a reasonable default.

3.4 — Persisting settings in .claude/settings.json

CLI flags are one-shot. For persistent project defaults, set them in .claude/settings.json (git-committed, shared with the team) or .claude/settings.local.json (local override, not committed).

// .claude/settings.json — shared project defaults
{
  "permissionMode": "acceptEdits",
  "disallowedTools": ["GitCommit", "GitPush"]
}

The example above sets acceptEdits as the default for everyone working in pacman-cpp20, and hard-blocks git commit and push at the project level. Individual developers can override locally, but the shared default prevents accidental commits from an unattended session.

The trap: permission mode is not a security boundary
Permission modes control the UX of approval — how much Claude Code interrupts you. They do not sandbox the process. Claude Code runs with your user permissions. If you are running as a user who can delete system files, dontAsk mode with a Bash tool and a badly scoped prompt can delete system files. The safeguard is: constrain the tool surface (--allowedTools), scope the working directory, and never run headless on a task you have not already understood in plan mode.

3.5 — Headless mode for CI/CD

Claude Code can run entirely non-interactively using claude -p (print mode) with --permission-mode dontAsk. This is how you wire it into a CI pipeline — for example, to run a code review pass on every pull request, or to auto-generate a CLAUDE.md diff after a merge.

# CI example: read-only analysis, output to file, no prompts
claude -p "Read CLAUDE.md and the .ixx files. Report any stale claims." \
  --permission-mode dontAsk \
  --allowedTools Read,LS,Glob,Grep \
  --output-format json \
  > audit-report.json

The --output-format json flag structures the response for machine consumption. Combined with -p and dontAsk, this is a fully scriptable pipeline step with zero human interaction.

3.6 — Permission modes and the delegation tiers

The T1–T4 tier model from your CLAUDE.md describes who drives the work. The permission model describes how much autonomy the agent has when it acts. They compose:

T1
You are writing. Claude Code is not involved. Permission mode is irrelevant — the agent is not running.
T2
You are writing, agent is answering questions. Use plan or default — the agent should read, not touch.
T3
Agent drafts, you own. Use acceptEdits — writes are expected, but you review before any shell execution. This is the right mode for CLAUDE.md edits, CMake boilerplate, SDL2 wiring.
T4
Full delegation. Use auto with --disallowedTools GitCommit,GitPush — let it run, but keep git operations in human hands until you have reviewed the output.

3.8 — Session close: permission hygiene checklist

After Module 3, apply this checklist to every Claude Code session you start from now on:

  • Know the permission mode before the session starts — never rely on the default by accident.
  • For exploration and review tasks: use plan mode. The agent cannot touch anything.
  • For active coding sessions (T3/T4 work): use acceptEdits with GitCommit and GitPush disallowed.
  • For fully automated tasks: use auto or dontAsk only after you have run the same task in plan mode and understood what it will do.
  • .claude/settings.json is committed and sets safe project defaults. settings.local.json is for personal overrides — not committed.
  • Git operations stay in human hands. Always. Add GitCommit and GitPush to disallowedTools at the project level.

Module 04 — Context management: fighting entropy

Lesson goal

By the end of this lesson you have a precise mental model of how the context window fills, how to control compaction, and how to recover a full working context after a reset in one shot. You will have experienced context pressure on a real task, used /compact with custom instructions, and established the CLAUDE.md bootstrap loop that makes long-lived work on pacman-cpp20 sustainable.

4.1 — The context window is a shared resource

The 200K token window is not just "how much Claude remembers." It is the working memory for everything — your messages, every file read, every tool output, every build log. A single flat pool shared by all of it.

A session that reads 20 .ixx files, runs two builds, and receives a 3000-line compiler error has already burned 30–40K tokens before you have typed a second meaningful prompt. On a C++ project like pacman-cpp20, context pressure is routine, not exceptional.

When the window fills, the model does not crash — it degrades. Responses get less precise. Earlier context drops. The agent starts losing architectural decisions it acknowledged an hour ago. The degradation is silent, which makes it dangerous.

Monitoring context pressure
Use /cost to see token counts. Use /context to visualise window fill as a percentage — more useful than raw numbers when deciding whether to compact. On a small project like pacman-cpp20, auto-compaction (80% threshold) may never fire in normal use. That does not mean context management is irrelevant — it means you need to use /compact proactively rather than reactively.

4.2 — /compact vs /clear

Two commands, very different semantics. The choice between them is a judgment call you make at a specific moment in a session.

/compact
Distill and continue. Replaces the full history with a model-generated summary, then keeps the session alive. You lose verbatim content but retain the shape of what happened — decisions made, current state, what is in progress. Think of it as a squash merge: the individual commits are gone, the diff is preserved. Use when there is still valuable in-session context that is not yet in CLAUDE.md.
/clear
Full reset. Blank context. Nothing carries over. Use when the session has gone sideways and the accumulated context is more noise than signal, or when pivoting to a completely different task. The question to ask before choosing: is there anything in this session that is not already in CLAUDE.md or the codebase? If no — or if the session is corrupt — clear it.

4.3 — Auto-compaction: the 80% threshold

Claude Code auto-compacts when the context hits 80% of the window. You do not trigger it — it fires automatically, and it does not ask you whether the summary is accurate.

The auto-summary is optimised for breadth. It keeps the gist. What it drops: the exact error message that led to an architectural decision, the precise module interface constraint you were working around, the T1/T2 boundary call you made an hour ago. These are exactly the things that matter most on a C++ project.

After any auto-compaction

Module 05 — Custom commands & skills

Lesson goal

By the end of this module you have two things working in pacman-cpp20: a set of project-scoped slash commands that encode your most-repeated workflows, and a C++ review skill that Claude Code invokes whenever you ask it to review code. You understand the distinction between commands (invoked explicitly, procedural) and skills (invoked by natural language, declarative), and you know when to use each.

5.1 — What commands are

A custom slash command is a markdown file in .claude/commands/. When you type /command-name in a session, Claude Code reads that file and executes it as a prompt. That is the entire mechanism — no plugins, no configuration, just a file.

The power is in what you put in the file. A good command is a distilled, reusable prompt that would otherwise take you 30 seconds to type from memory, get slightly wrong, and re-issue. Commands eliminate that friction permanently.

.claude/
  commands/
    build.md          # /build  — run the project's standard build
    review.md         # /review — trigger code review against project standards
    status.md         # /status — report phase state and open items from CLAUDE.md

Commands are committed to git. Every developer on the project gets them. They are the shared vocabulary of your Claude Code workflow — the same way CLAUDE.md is the shared context.

5.2 — Anatomy of a command file

Command files are plain markdown. Claude Code reads the file content and treats it as the prompt. There is no special syntax required — but a few patterns make commands significantly more useful.

Minimal command

# build.md
Run the clang-ninja-debug build using the preset. Report all warnings and errors with file name and line number. If the build succeeds, confirm with the binary path.

Invoked as /build. Claude Code reads the file, executes it as a prompt. The exact command it runs is determined by CLAUDE.md — which is why a well-maintained CLAUDE.md makes commands more reliable.

Parameterized command with $ARGUMENTS

# review.md
Review the following file or module: $ARGUMENTS

Apply the pacman-cpp20 review checklist (see .claude/skills/cpp-review.md).
Report findings grouped by severity: Error, Warning, Note.

Invoked as /review src/game.stage.ixx. The string after the command name is substituted for $ARGUMENTS. If no argument is given, Claude Code will usually ask — or you can add a fallback instruction in the file.

$ARGUMENTS is positional, not named
$ARGUMENTS is the entire string after the command name — one substitution, no named parameters. For simple use cases this is sufficient. If you need more complex parameterisation, encode the structure in natural language: "the first word is the module name, the rest is the task description." Claude Code will parse it correctly.

5.3 — Commands worth building for pacman-cpp20

Three commands cover the majority of the repetitive workflow in this project:

/build

Run the standard debug build, surface all errors and warnings, confirm the binary path. You type this multiple times per session — encoding it saves nothing in keystrokes, but it ensures you always get consistent output format and never misremember the preset name.

/status

Read CLAUDE.md, extract the Current Status section, report the current phase, all open items, and the next action. Useful at session start before you begin work, and after any compaction to verify the summary was accurate.

/review $ARGUMENTS

Review a named file or module against the project's C++ review skill. The skill defines the criteria — the command is the trigger. Covered in depth in 5.6.

5.4 — What skills are

A skill is a markdown file in .claude/skills/ (or .claude/ directly — the location is a convention, not a requirement). Unlike commands, skills are not invoked by a slash prefix. They are referenced by other prompts — either directly by name, or by a command that includes them.

Think of a command as a function call and a skill as a library it imports. The command says "review this file." The skill says "here is what a review means in this project." Separating them means you can update the review criteria once — in the skill file — and every command that references it gets the update automatically.

The mental model
Commands are procedural: do this sequence of steps. Skills are declarative: here is what good looks like. A command without a skill is a shortcut. A skill without a command is documentation. Together, they are executable standards.

5.5 — Skill discovery: how Claude Code finds skills

Claude Code does not automatically scan for skill files. A skill is active in a session when it is either:

  • Explicitly referenced in a command file — see .claude/skills/cpp-review.md
  • Mentioned in CLAUDE.md — e.g. a note that a review skill exists and where it lives
  • Loaded by you directly — ask Claude Code to read the file at session start

The practical pattern: reference your key skills in CLAUDE.md so they are part of the session bootstrap. One line is enough: Code review criteria: .claude/skills/cpp-review.md. Claude Code will read it when it reads CLAUDE.md.

5.6 — Building the C++ review skill for pacman-cpp20

A review skill is a checklist encoded as instructions. For pacman-cpp20 the relevant criteria fall into four categories:

Module hygiene

  • Interface units (.ixx) export only what downstream modules need — no implementation detail leaking through export
  • Implementation units (.cpp) import their own module first, before all others
  • No circular imports — check against the module graph in CLAUDE.md
  • Module names match file names (game.stage → game.stage.ixx)

C++20 feature use

  • Concepts are constraining real template parameters — not used decoratively
  • Coroutines: co_await / co_return only in functions with a coroutine return type. No mixing of coroutine and non-coroutine logic in the same function
  • No raw owning pointers where a smart pointer or value type would do
  • No using namespace std in interface units

ECS pattern compliance

  • Components are data only — no logic, no virtual functions
  • Systems operate on components via the registry — they do not hold component state themselves
  • Entity IDs are not stored as raw integers outside of ECS-aware code

Naming and style

  • Member variables: trailing_underscore_
  • Types: PascalCase
  • Free functions and methods: snake_case
  • No abbreviations in public API names — elapsed_seconds not elps

The skill file encodes exactly these four sections as instructions. The /review command references it. This is T3 content — you write the criteria (that is T1: it reflects your architectural decisions), the agent applies them mechanically.

5.7 — Commands vs skills vs CLAUDE.md — the decision matrix

CLAUDE.md
Persistent facts about the project: architecture, build system, module graph, delegation model, current phase. Things the agent needs to know at session start, every session. Not invocable — always loaded.
Commands
Repeated procedural workflows you trigger explicitly: build, review, status check. Invoked by /name. The prompt is the file content. Best for actions with a clear start and expected output.
Skills
Standards and criteria the agent applies when doing work: what a review means, what a well-formed module looks like, what the ECS rules are. Not invoked directly — referenced by commands or loaded at session start. Best for "what good looks like" knowledge that multiple commands share.

The rule of thumb: if you find yourself writing the same instruction more than once — in a command, in a prompt, in CLAUDE.md — it belongs in a skill. Extract it once, reference it everywhere.

Module 06 — Hooks — deterministic automation

Lesson goal

By the end of this module you have a build-on-write hook active in pacman-cpp20. Every file write triggers a CMake build automatically. You understand the four lifecycle events, the difference between blocking and reacting, and when to reach for a hook instead of a command or skill. You also understand the current Claude Code bug affecting PreToolUse deny decisions for Write/Edit tools, and have documented it clearly for when the fix lands.

6.1 — The problem hooks solve

Skills and commands rely on the model to invoke them. The model can forget. It can skip a step if it decides the step is unnecessary. For things that must always run — a build after a write, a path check before a file is created — model-driven invocation is the wrong tool.

Hooks are shell commands that Claude Code runs automatically at specific points in its execution lifecycle, regardless of what the model decides. The model has no say in whether a hook fires. That is the point.

The analogy: hooks are like PostBuildEvent in MSBuild or a Git pre-commit hook. They are not suggestions. They run.

6.2 — The hook lifecycle

Claude Code exposes four primary lifecycle events:

PreToolUse

Fires before a tool call executes. The hook can inspect the pending call and return a deny decision to block it. The tool never runs. Use case: block writes to protected paths, enforce naming conventions before a file is created.

PostToolUse

Fires after a tool call completes. The hook receives the tool name, input, and output. The write already happened — you are reacting, not blocking. Use case: auto-build after a file write, run clang-format after an edit.

Notification

Fires when Claude Code emits a notification. Use case: desktop alerts, Slack pings on long-running tasks.

Stop

Fires when the agent finishes its turn. Use case: session-level automation — run the test suite on close, log cost, write a session summary.

Key asymmetry: PreToolUse can prevent. PostToolUse can only react. Once a write has happened, the hook can tell the agent about it — but it cannot un-write the file.

6.3 — Hook configuration

Hooks live in .claude/settings.json under a "hooks" key, alongside permissionMode and disallowedTools:

{
  "permissionMode": "acceptEdits",
  "disallowedTools": ["GitCommit", "GitPush"],
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/build-on-write.sh"
          }
        ]
      }
    ]
  }
}

matcher — a regex matched against the tool name. Write|Edit|MultiEdit catches every file-modifying tool. An overly broad matcher fires on reads too — match precisely.

type — currently only "command" is supported. Relative paths resolve from the project root. For anything non-trivial, use a script file rather than an inline command.

Composability — the top-level key is the lifecycle event, inside that is an array of matchers, each with its own array of hooks. Multiple hooks on the same event compose via the array. JSON does not allow duplicate keys — multiple matchers go in the array, not as separate top-level entries.

6.4 — What the hook receives

When PostToolUse fires, your script receives a JSON object on stdin. Key fields:

{
  "hook_event_name": "PostToolUse",
  "tool_name": "Write",
  "tool_input": {
    "file_path": "C:\\DEV\\pacman-cpp20\\src\\game\\stage.ixx",
    "content": "..."
  },
  "tool_output": "File written successfully"
}

Note: the path key is file_path, not path. On Windows, Claude Code passes the full absolute path with backslashes. Hooks that parse stdin must account for this. The CLAUDE_TOOL_INPUT_FILE_PATH environment variable is documented but not reliably set on Windows — parse stdin instead.

For the build hook, you can ignore stdin entirely and just run the full build. The stdin data is there when you need it.

6.5 — The pacman-cpp20 build hook

The script at .claude/hooks/build-on-write.sh:

#!/usr/bin/env bash
set -euo pipefail

BUILD_PRESET="clang-ninja-debug"
PROJECT_ROOT="$(git rev-parse --show-toplevel)"

cd "$PROJECT_ROOT"

cmake --build --preset "$BUILD_PRESET" 2>&1 | \
  grep -E "(error|warning):" | \
  head -40 || true

Four details matter:

  • set -euo pipefail — exits on failure, treats unset vars as errors, propagates pipe failures.
  • 2>&1 — CMake writes errors to stderr. Without this redirect, grep never sees them.
  • grep -E "(error|warning):" | head -40 — cost control. Raw cmake output is verbose. Filter to what matters, cap the line count.
  • || true — when grep finds no matches (clean build), it exits 1. Without || true, set -e kills the script silently. Clean builds should produce no output and exit 0.

On a clean incremental build, the hook produces no output — nothing recompiled, nothing to surface. This is correct and cheap. Output only appears when there is something actionable.

6.6 — Controlling hook output and exit codes

Hook stdout is fed back to the model as context. Every line costs tokens on every write. Keep output tight.

Exit code semantics for PostToolUse: exit 0 = informational, agent continues. Non-zero = hook signals a problem, agent turn interrupted by default. Add "continueOnBlock": true to the hook entry to surface failures without interrupting the turn — useful for linters, not for build errors.

Exit code semantics for PreToolUse: exit 0 = allow. The deny decision is carried in a JSON object on stdout, not via exit code alone:

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "reason here"
  }
}

6.7 — The decision matrix

Hook
Automatic, lifecycle-driven. Deterministic. Use when something must always happen regardless of model behaviour — build on write, path guard before create. Config: settings.json.
Command
Explicit invocation via /name. Model-dependent. Use for repeated workflows you trigger deliberately — /build, /review. Config: .claude/commands/.
Skill
Natural language invocation. Model-dependent. Use for domain standards and criteria that should inform how the agent acts throughout a session. Config: .claude/skills/.

The routing question: "What happens if this doesn't run?" Broken state or silent failure → hook. Wasted time retyping → command. Agent acting without the right standards → skill.

6.8 — PreToolUse: blocking writes to protected paths

PreToolUse lets you enforce guardrails the permission model cannot express. The guard script for pacman-cpp20 blocks any write to a .ixx file outside src/:

#!/usr/bin/env bash
# .claude/hooks/guard-module-writes.sh

INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | python -c "
import sys, json
d = json.load(sys.stdin)
path = d.get('tool_input', {}).get('file_path', '')
print(path)
")

NORMALIZED=$(echo "$FILE_PATH" | tr '\\' '/')

if [[ "$NORMALIZED" == *.ixx && "$NORMALIZED" != */src/* ]]; then
  echo '{
    "hookSpecificOutput": {
      "hookEventName": "PreToolUse",
      "permissionDecision": "deny",
      "permissionDecisionReason": ".ixx files must live in src/. Got: '"$FILE_PATH"'"
    }
  }'
  exit 0
fi

exit 0
Known bug — Claude Code issue #37210
permissionDecision: "deny" is honoured for Bash tool calls but silently ignored for Edit and Write — the file is modified anyway. Filed March 2026, open. The script is correct and committed; re-enable in settings.json once the fix lands. For blanket tool bans, use disallowedTools instead — that path is reliable.

7.1 — The problem subagents solve

Every file read, every tool output, every build log fills the same 200K context window. A session that explores 30 source files before finding the right one has burned 15–20K tokens on navigation noise — tokens that are now permanently part of the session history and priced on every subsequent turn.

Subagents are isolated Claude sessions you spawn from the main session. They have their own context window, their own tool set, their own model. The main session delegates a bounded task, the subagent runs to completion, and only the summary returns. The exploration noise never enters your main window.

The analogy from engine work: spawning a subagent is like forking a background thread with a narrow job description and a callback. The main thread stays clean. The fork does the dirty work and reports back.

When to delegate — and when not to

Delegate when: (1) the task produces verbose output the main session does not need to remember verbatim, (2) the task is a side query that would inflate context before the real work starts, (3) multiple independent tasks can run in parallel. Do not delegate when: the task is small (a direct tool call is cheaper), the subagent result needs tight integration with ongoing context, or the task is T1/T2 work where you need to read the output live.

7.2 — The three built-in subagent types

Claude Code ships three built-in subagents. You rarely invoke them explicitly — the main agent routes to them automatically based on task characteristics. Understanding what they are tells you what Claude is doing when it spawns them.

Explore

Read-only. Runs on Haiku by default — fast, cheap, disposable. Used for codebase search and discovery: "which files touch the ECS registry?", "where is the ghost AI state machine?". The result is a concise summary. The file reads never enter the main context.

Plan

Gathers context before presenting a strategy in plan mode. Fired automatically when the main agent enters plan-before-execute mode and needs to read supporting files first.

General-purpose

Read and write. The default when a task involves both exploration and modification. Used for self-contained delegated tasks: "add a unit test for this function", "update the CHANGELOG".

The auto-selection is imperfect. A task that sounds read-only may get routed to general-purpose. Explicit invocation via @agent-name or a custom subagent definition gives you precise control.

7.3 — Custom subagents: the .claude/agents/ contract

Custom subagents are Markdown files with YAML frontmatter. The frontmatter is the configuration; the Markdown body is the system prompt.

# .claude/agents/cpp-scout.md
---
name: cpp-scout
description: >
  Read-only codebase scout for pacman-cpp20. Use this agent when you need
  to search for symbol definitions, trace module dependencies, or find all
  sites where a specific type or function is used — without making any edits.
  Do not use for tasks that require writing files.
tools: Read, Grep, Glob, LS
model: claude-haiku-4-5-20251001
---

You are a read-only scout for the pacman-cpp20 codebase.

Your job: find and report. Never write, edit, or delete files.

When searching for a symbol, check .ixx interface units first, then .cpp
implementation files. Report: file path, line number, the relevant snippet
(3 lines of context max), and one sentence on what you found. Stop when you
have a complete answer. Do not include raw file dumps.

Key decisions in this definition:

  • tools — scoped to read-only tools only. A scout that can write is not a scout.
  • model — Haiku for search tasks. The cost differential over Sonnet is 10–20x; use it.
  • description — this is how the main agent decides to invoke the subagent automatically. Write it as trigger conditions, not just a label. "Use this agent when…" is the right register.

7.4 — Scope and discovery

Two scopes, same pattern:

Project scope
.claude/agents/<name>.md — committed to the repo, shared with the team, versioned with the codebase. The right place for project-specific scouts and review agents.
User scope
~/.claude/agents/<name>.md — personal, applies across all your projects. The right place for general-purpose helpers that are not project-specific.

Claude Code reads both on startup and merges them. Project-scope definitions override user-scope on name collision.

7.5 — Invocation

Three ways to invoke a subagent:

Automatic. The main agent reads all agent descriptions at session start and routes to the right one based on the task. If your description is precise and the task matches, this just works. If the wrong agent fires — or none fires — use explicit invocation.

Explicit in-session. Type @cpp-scout find all call sites of Registry::create_entity in the REPL. The @ prefix targets the named agent directly, bypassing automatic routing.

Prompt delegation. Inside a prompt: "Use the cpp-scout agent to locate all places where PacmanComponent is accessed, then use those results to…". The main agent spawns the subagent, waits for the result, and continues with the summary.

7.6 — Parallel dispatch

The highest-leverage subagent pattern: independent tasks that would be slow sequentially. The main agent can spawn multiple subagents concurrently; they run in parallel and the parent waits for all results before continuing.

Use the cpp-scout agent in parallel to: (1) find all modules that import game.stage, (2) find all types that implement the Renderable concept, (3) find all locations where SDL_RenderFillRect is called. Report the three results together.

Three separate file searches, each with noisy output, running concurrently. The main context receives three clean summaries. Without delegation, this would be one sequential search and the raw output of each grep would fill the window.

Token cost reality check
Each subagent runs on its own context. Parallel subagents multiply token consumption proportionally — three concurrent Haiku scouts cost approximately three times a single scout. At Haiku pricing this is still cheap, but worth tracking with /usage after your first parallel dispatch to calibrate your intuition.

7.7 — Frontmatter reference

Complete list of supported frontmatter fields:

---
name: my-agent              # identifier used by @invocation
description: >              # trigger description — write as conditions
  Use when...
tools:                      # allowlist — omit to inherit parent's full set
  - Read
  - Grep
  - Glob
  - LS
  - Bash                    # include only if the agent needs to execute
  - Write                   # include only if the agent needs to write
disallowedTools:            # explicit denylist — alternative to allowlist
  - Write
  - Edit
model: claude-haiku-4-5-20251001   # override model — default inherits parent
permissionMode: default     # default | acceptEdits | auto
maxTurns: 10                # cap agent turns — prevent runaway agents
---

Use tools (allowlist) when you want a tightly scoped agent. Use disallowedTools when you want to inherit most capabilities but block specific ones. Use maxTurns for exploration agents where an unbounded run is a bug, not a feature.

7.8 — Subagents vs skills vs commands — completing the decision matrix

CLAUDE.md
Always-loaded facts. Architecture, build system, delegation model. Not invocable.
Commands
Explicit procedural workflows. /build, /review target.ixx. Main agent runs them in the main context.
Skills
Standards and criteria. What a good module looks like, ECS rules, naming conventions. Referenced by commands, not executed independently.
Subagents
Isolated workers. Bounded tasks with noisy intermediate output you do not want in the main context. Especially: exploration, parallel search, self-contained edits with no main-context dependencies.

The test: does the task produce output your main session needs to remember in detail? If yes — keep it in the main context. If no — delegate.

8.1 — What MCP is

MCP (Model Context Protocol) is the standard that lets Claude Code call tools outside itself. Each MCP server is a process that exposes a set of named tools. Claude discovers them at startup and can call them exactly like its built-in tools — the model sees no difference between Read and github_list_issues. That is the point.

The analogy: MCP is to Claude Code what a driver is to an OS. The OS (Claude) does not know about your specific hardware (GitHub, Sentry, your database) — the driver (MCP server) speaks a common protocol and the OS calls it uniformly.

When to connect a server
When you catch yourself copy-pasting content from another tool into the session. Issue tracker, monitoring dashboard, PR list — if it is travelling through your clipboard to reach Claude, MCP eliminates that round-trip.

8.2 — Transports

MCP servers communicate over one of four transports:

  • HTTP (recommended for remote services) — standard for cloud-hosted servers. Supports OAuth natively. GitHub, Sentry, Linear, Notion all use this.
  • stdio (local processes) — server runs as a subprocess, Claude communicates over stdin/stdout. Ideal for local tools with direct filesystem access or custom scripts.
  • SSE — deprecated. Was the original remote transport. Still works; use HTTP instead. You will see it in older guides.
  • WebSocket — persistent bidirectional connection. Only needed when the server pushes events unprompted. Not supported by claude mcp add --transport; configure via .mcp.json directly.

For the GitHub exercise in this module: HTTP transport, PAT auth.

8.3 — Three scopes

The scope names changed from older documentation. This is the current state:

Scope Who sees it Where stored Use case
local (default) You, current project only ~/.claude.json Personal/experimental, credentials you do not want in VCS
project Everyone on the team .mcp.json in project root, committed to VCS Shared tooling — same servers for the whole team
user You, all projects ~/.claude.json Tools you use everywhere: GitHub, your DB, monitoring
Critical scope correction
project scope does not mean "private to you in this project." It means shared with the team via version control — the config lands in .mcp.json which is designed to be committed. Never put raw credentials in a project-scoped config. Use env var expansion (${GITHUB_PAT}) instead.

Both local and user scope are stored in ~/.claude.json — but in different sections. local is stored under a project-path key (only loads in that project). user is stored at the top level (loads everywhere). Same file, two sections.

Precedence when the same server is defined at multiple scopes: local > project > user > plugin-provided.

8.4 — Adding servers

# Remote HTTP server (most common)
claude mcp add --transport http <name> <url>

# With auth header
claude mcp add --transport http github https://api.githubcopilot.com/mcp/ \
  --header "Authorization: Bearer YOUR_PAT"

# Local stdio server — options before name, -- separates name from command
claude mcp add --transport stdio --env KEY=value <name> -- npx -y some-server

# Explicit scope
--scope local    # default, private to you in this project
--scope project  # writes to .mcp.json, shared via VCS
--scope user     # available in all your projects

# Management
claude mcp list          # list all servers + status
claude mcp get github    # details for one server
claude mcp remove github # remove it

Servers from .mcp.json that have not been approved yet show as ⏸ Pending approval in claude mcp list. Run claude interactively to review and approve them. The /mcp slash command shows live server status and handles OAuth flows from inside a session.

8.5 — Authentication patterns

PAT (Personal Access Token) — what you use for GitHub. Pass as a header. Use fine-grained PATs (not classic) — they let you scope to specific repositories.

Never hardcode tokens in .mcp.json
That file is designed to be committed. Use env var expansion instead: "Authorization": "Bearer ${GITHUB_PAT}". The variable is expanded at server startup from your shell environment. If the variable is not set, Claude Code fails to parse the entry rather than connecting with an empty token.

OAuth — what most hosted services use (Sentry, Linear, Notion). Claude Code handles the full flow. When a server responds with 401 or 403, it flags in /mcp so you can complete the browser auth. Token stored in keychain (macOS) or a credentials file, refreshed automatically.

The practical rule: static API key → header auth. OAuth-capable server → prefer OAuth. No tokens land in config files.

PAT scope and multiple projects: a user-scoped server uses one PAT across all projects. Fine-grained PATs let you select specific repositories explicitly — start narrow and expand as needed. If you need to mix personal and employer repos with different access levels, register separate servers (github-personal, github-work) backed by separate PATs.

8.6 — Token limits

Two env vars to know:

  • MAX_MCP_OUTPUT_TOKENS — hard ceiling on tokens per tool call output. Default: 25,000. Claude Code warns at 10,000. Set higher if a tool (e.g. a large DB schema query) legitimately needs it: export MAX_MCP_OUTPUT_TOKENS=50000
  • ENABLE_TOOL_SEARCH — by default, MCP tool definitions are deferred: only tool names load at startup, schemas load on demand. This keeps context lean. Set to false to load everything upfront (not recommended unless you are debugging tool routing).

The practical implication: adding 10 MCP servers does not bloat your context the way 10 large @ file reads do. Tool search handles deferred loading transparently.

8.7 — MCP vs subagents — completing the architecture picture

MCP sits in the Extension layer, not the Delegation layer. The distinction matters:

  • A subagent (M7) is a separate Claude instance — it has its own context, reasons, and decides. You delegate tasks to it.
  • An MCP server is a dumb tool surface — it executes what Claude tells it and returns data. No reasoning happens inside it.

MCP expands what Claude can act on. Subagents expand what Claude can delegate reasoning to. They compose: a subagent can call MCP tools just like the main session can.

Module 09 — Cost, model selection & sustainable usage

Lesson goal

By the end of this lesson you have a clear mental model for what drives cost and quota consumption, you can make deliberate model selection decisions rather than defaulting to whatever is active, and you understand the two independent levers that control speed: Fast Mode and effort level. You also have the five habits that prevent runaway context from killing both quality and budget.

9.1 — The three variables that drive cost

The cost question in Claude Code is not "how much does Opus cost per token." It is: what determines total session spend, and how do you control it? Three variables drive the answer.

Variable 1 — Context size

Every turn sends the entire conversation history to the model. A session that has read 20 files, produced 10 diffs, and debugged through 30 messages is paying for all of that on every subsequent message. Context is cumulative — and it is the dominant cost driver, not model selection. This is M4 and M9 as the same lesson from different angles.

Variable 2 — Model tier

Three families: Haiku (fast, cheap), Sonnet (default, right for ~80% of work), Opus (deeper reasoning, more expensive, more quota). On API billing the cost differential between Sonnet and Opus is roughly 5–8× on input, 6–10× on output. On subscription plans the effect is quota burn rate rather than dollar cost.

Variable 3 — Task count per session

Each unrelated task you stack onto an existing session adds to the running context. Clearing between tasks is the highest-ROI habit because it zeroes out variable 1. Simple test: if your next prompt would make sense in a brand-new terminal, run /clear first.

9.2 — Billing mode: two different worlds

How your account is set up determines how cost surfaces — and which command to use.

Subscription plans (Pro / Max / Team Premium / Enterprise seat)

Flat monthly fee with a usage quota that resets on a rolling window (~5 hours for individual limits). You see quota consumption, not a dollar counter. When you hit the limit, Claude Code shows when the window resets. The relevant command is /usage. Default model depends on tier: Pro gets Sonnet 4.6; Max / Team Premium / Enterprise pay-as-you-go get Opus 4.8.

Note: In recent versions, /cost and /usage appear to be aliases — both return the same output. Verify with /model what tier your account defaults to.

API key (Console, Bedrock, Vertex, Foundry)

Pay per token, billed to your account. No monthly cap, no hard stop. The relevant command is /cost — it shows running spend for the current session. On a long agentic session with a codebase like pacman-cpp20, 100K–200K input tokens per session is routine. With three concurrent subagents, multiply proportionally.

API billing punishes long uncleared sessions far more visibly than subscription billing. Both benefit from the same habits, but the feedback loop is sharper on API.

9.3 — Model selection: /model and its aliases

Run /model at any time. No arguments opens the interactive picker; /model <alias> switches immediately. Context and history carry over — only the model processing your next message changes.

/model              # open picker
/model sonnet       # switch to Sonnet 4.6 — default for most work
/model opus         # switch to Opus 4.8 (API) / 4.7 (AWS)
/model haiku        # switch to Haiku 4.5 — cheap, fast, mechanical tasks
/model opusplan     # Opus during plan mode → Sonnet for execution
/model opus[1m]     # Opus with 1M token context window

opusplan is the most underused alias. It gives you Opus-quality planning (where reasoning pays off) and Sonnet execution (where the work is mostly mechanical). Use it as the default for any session involving architectural decisions or multi-file changes.

Project-level model default
Pin a model for a specific project in .claude/settings.json: { "model": "opusplan" }. Sets the startup default; users can still override with /model.

9.4 — Effort levels

A second, independent axis from model selection. /effort controls how much the model reasons per step. Available on Opus 4.8, Opus 4.7, Opus 4.6, and Sonnet 4.6.

/effort             # open picker
# Levels: low · medium · high (default) · xhigh · max
# low/medium/high/xhigh persist across sessions
# max applies to current session only

Lower effort is faster and cheaper for straightforward tasks. Unlike /model, effort affects quality, not just speed — dropping effort to low on a complex architectural question will produce shallower output. It is not a substitute for switching to Haiku; it is a reasoning depth knob on the current model.

9.5 — Fast Mode

Fast Mode is a high-speed configuration for Opus 4.6, making it 2.5× faster at higher token cost ($30/$150 per MTok input/output). It is not a different model — same weights, different API configuration optimized for latency over cost efficiency.

/fast               # toggle on/off. ↯ indicator appears when active

Fast Mode vs effort level

Fast Mode = same quality, lower latency, higher cost. The trade is money for speed.
Lower effort = less reasoning time, faster responses, potentially lower quality. The trade is quality for speed.
They are orthogonal — you can combine both for maximum speed on straightforward tasks.

Fast Mode constraints
Research preview. Available only on subscription plans via extra usage (billed at fast mode rates from the first token, bypassing your plan's included quota). Not available on Bedrock, Vertex, or Azure Foundry. Requires extra usage credits to be enabled. If your organization has not explicitly enabled it, /fast returns a disabled message.

9.6 — The decision framework

# Task is: small, mechanical, repetitive (grep, rename, boilerplate)?
→ Haiku. Or delegate to a Haiku subagent if it would bloat main context.

# Task is: standard coding work (feature, fix, test, refactor)?
→ Sonnet. Covers ~80% of your day.

# Task is: complex reasoning (architecture, hard bug, cross-cutting refactor)?
→ opusplan. Opus writes the plan. Sonnet executes it.

# Starting a new unrelated task?
→ /clear first. Dead context is the main cost driver.

# Mid-task, context filling up?
→ /compact. Not /clear — you need the history.

# On API billing, long autonomous run?
→ Track with /cost. Exploration tasks → Haiku subagent (M7 pattern).

9.7 — What actually consumes tokens

Every turn sends three things to the model: the full conversation history, project context (CLAUDE.md + files read this session), and your new prompt. Of these, conversation history is the dominant driver — it grows with every turn.

  • CLAUDE.md is included on every turn. Prompt caching makes subsequent turns cheap (cache-read rates), but it still occupies window space. Keep it under ~200 lines.
  • MCP tool results (M8) accumulate in context. MAX_MCP_OUTPUT_TOKENS is a cost knob, not just a stability guard.
  • Subagent token cost (M7): parallel subagents multiply consumption proportionally. Three concurrent Haiku scouts cost ~3× a single scout. Parallel Opus subagents on API billing is expensive fast.
  • Once a file is in context, follow-up questions about it are nearly free. The expensive operation is the first read. Batch related file reads into one session rather than starting fresh for each question.
  • /clear resets conversation, not the process. /cost and /usage report the full process lifetime. For a clean cost baseline, restart the process entirely (/exit then claude).

9.8 — Subscription vs API: when to switch

Subscription is better when

  • Usage is consistent and daily
  • You want predictable monthly cost
  • You are working on a single development machine

API key is better when

  • Usage is irregular or bursty
  • You want exact per-session cost visibility
  • You are building CI pipelines or headless tooling
  • You need fine-grained model version pinning

The hybrid approach: subscription as baseline, API overflow for spikes. Subscription optimizes for predictability; API handles peaks without upgrading tiers permanently. Note: Anthropic has adjusted subscription quotas several times in 2026 — the tier prices (Pro $20/month, Max 5×/$100, Max 20×/$200) have been stable, but the quota inside each tier has moved. Check the current help center before making a tier decision.

Animation system — shape-based, no sprites

A first-class 2D shape animation system. The design constraint is intentional: no bitmaps, no sprite sheets. Everything is constructed from geometric primitives animated over time. This forces you to think about animation as a mathematical relationship between time and shape parameters — the right abstraction for a coroutine-driven system.

Two categories (already sketched in PROJECT.md):

  • Looping animations — pure functions of elapsed_. Pac-Man mouth, ghost body wobble. No coroutines. An oscillating scalar drives shape parameters in draw().
  • One-shot sequences — timed sequences with suspension. Death spiral, frightened flash, level-clear. Natural coroutine territory: co_await timer(duration) replaces state enums and frame counters.

Gameplay extensions (post-Phase 4)

  • Multiple mazes with different topologies
  • Power-up variety beyond the classic power pellet
  • Configurable ghost behaviour via data-driven parameters
  • A level editor leveraging the same shape-rendering pipeline
